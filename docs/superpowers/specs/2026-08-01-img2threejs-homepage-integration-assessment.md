# img2threejs 在个人主页中的接入评估

## 结论

`img2threejs` 可以用于当前个人主页，建议把它作为键盘、鼠标、机箱、台灯等真实硬表面物件的优先重建方法。

这里的“可以用”不是指上传一张图后直接得到可发布模型，而是指它能把参考图转成可审查、可修改、可版本管理的 Three.js / TypeScript 物件工厂，并能接入当前已经模块化的桌面场景。它更像一套带质量 Gate 的程序化建模流程，不是摄影测量，也不直接输出 `.glb`、`.obj` 或 `.fbx`。

正式接入必须满足以下条件：

- 每次只处理一个物件，不重建整张桌面。
- 先在独立实验页完成多角度验收，再进入主页场景。
- 自动生成结果只作为初稿，必须允许继续修改规格和源码。
- 视觉评分达到 `90/100`，并由尔玉确认后，才允许成为默认物件。
- 不改变现有拖动、点击、主屏光标映射、资源释放和页面布局。
- 继续通过资源预算、模型来源、构建和发布 Gate。

## 调研依据

### 微信文章

文章《开源一周斩获 7.4K Star！一张图片，一段代码，一个能跑能动的 3D 世界！》介绍的项目就是 `img2threejs`。文章对它的核心描述基本准确：输入参考图，输出 `ObjectSculptSpec` 与 TypeScript Three.js 工厂；模型由可命名的几何、材质、枢轴和插槽组成，并按 blockout、结构、形体、材质、表面、灯光、交互和优化分阶段验收。

需要修正的理解是：它不是传统意义上的“一张图片自动生成完整三维网格”。单张图片看不到的背面、底面和遮挡结构仍然需要推断；连续曲面和复杂材质也通常需要人工或 Agent 继续精修。

本机已使用当前 Skill 对仓库中的 G502 参考图执行预检：

```text

technicalSuitability：pass
warnings：0
```

随后在临时目录成功生成 `complex` 级预评估，质量合同要求至少：

- 3 个宏观组件
- 8 个中观组件
- 5 组微观细节
- 3 层材质
- 1 套重复结构
- 4 个评审视角
- 10 项身份细节清单

本地规格检索也正常命中 `core_3d` 资料。说明当前机器可以运行 intake、预评估、规格与质量 Gate；真正的物件分类、隐藏面判断和视觉评分仍必须由 Agent 对参考图与渲染图进行判断。

## 已有 G502 试验说明

仓库分支 `codex/g502-img2threejs-local` 已经完成过一次真实试验，不能忽略这条证据：

- 自动生成工厂：`mouse-g502.generated.ts`，约 `85,723` 字节源码。
- 本地精修工厂：`mouse-g502.refined.ts`，约 `15,901` 字节源码。
- 自动生成版视觉评分：`38/100`。
- 四轮精修后的本地候选：`82/100`。
- 当前结论：达到内部预览门槛，没有达到 `90/100` 的默认接入门槛。
- 剩余问题：掌托与前键区的曲面连续性、滚轮井与 DPI 区、左侧狙击键、尔玉 `E` 标志的位置和角度。

这次试验说明工具路线成立，但也说明不能把生成器结果直接视为成品。对鼠标这类连续曲面硬件，较可靠的方式是让 img2threejs 负责分析、规格、部件结构与初稿，再由我们针对轮廓和曲面重写关键几何。

## 与当前代码的兼容性

当前主页的鼠标由 `src/desktop/objects/mouse.ts` 创建，外层已经包含：

- `SceneObjectResult` 物件合同
- 独立拖动容器
- 透明命中代理
- 主屏光标同步
- 程序化与 GLB 视觉切换
- 加载失败回退
- 页面卸载与资源释放

img2threejs 的核心输出是返回 `THREE.Group` 的 TypeScript 工厂，因此可以只替换 `proceduralVisual`，保留外层交互和生命周期。它不需要重写场景、射线、拖动或主屏映射。

不能直接照搬实验目录中的完整生成代码。实验版把展示环境、相机、灯光、检查控制器和生成证据一起导入，约 `100 KB` 源码；当前首页 JS 为 `610,310` 字节，预算上限为 `650,000` 字节，静态整包接入很可能越过预算。

正式生产适配应当：

1. 只保留物件工厂和必要材质，不导入实验页的环境、相机与展示控制器。
2. 将生成证据、评审 JSON 和对照图留在 `modeling/img2threejs/<object-id>/`，不进入首页运行包。
3. 继续使用简单命中代理，不让高细节网格直接参与拖动射线检测。
4. 对重复结构使用 `InstancedMesh`；键盘键帽不能逐个复制完整材质和几何。
5. 在需要时使用动态导入形成独立 chunk，但默认物件加载不能造成明显闪烁。
6. 在 `check:models` 中增加 `procedural-ts` 资产类型，记录工厂路径、参考图来源、Skill 版本、坐标、尺寸、源码预算、评审分数与批准状态。
7. 默认物件切换仍采用显式批准字段；候选版只能通过查询参数或实验页查看。

## 适合与不适合的对象

### 优先适合

- 鼠标、键盘、机箱、显示器支架、台灯等硬表面物件。
- 需要拖动、点击、拆件、开合或灯光控制的对象。
- 需要长期在 Git 中继续微调尺寸、材质和品牌元素的对象。
- 允许“真实轮廓 + 轻度卡通化材质”的主页场景。

### 有条件适合

- Q 版人物摆件：可以做风格化重建，不能承诺人脸级精确还原。
- 高反光、透明或有复杂涂层的物件：需要额外照片和材质对照。
- 键盘：结构适合，但键帽数量会带来 draw call 和包体压力，必须实例化并简化不可见细节。

### 不建议使用

- 需要工业扫描精度或完全真实背面的产品展示。
- 毛发、布料、植物等复杂有机表面。
- 主体被遮挡、严重透视、低分辨率或只剩局部的一张照片。
- 徽章图案本身。徽章更适合“简单有厚度的底座 + 原图纹理或贴花”，不需要完整 img2threejs 流程。

这些情况应改用 Blender、摄影测量或神经网格工具生成 GLB，再经过现有 GLB 管线压缩和接入；或者明确接受风格化近似。

## 尔玉需要提供的素材

每个真实物件单独提供一个小资料包：

1. 物件名称、型号和准备放在桌面的哪个位置。
2. 俯视或主视图一张，主体完整，建议长边至少 `2000 px`。
3. 左前、右前、后侧各一张；底部结构重要时再补底视图。
4. 尽量使用均匀光线、干净背景，避免广角畸变、强反光和手部遮挡。
5. 长、宽、高的真实尺寸；没有精确尺寸时，在旁边放直尺或已知尺寸物体。
6. 哪些部件需要独立移动或点击，例如滚轮、按键、灯罩。
7. 哪些品牌标志保留、删除或替换成尔玉 `E`。
8. 哪些磨损、灰尘和线缆需要保留或忽略。
9. 确认照片可以用于公开主页；原始照片默认保留在本机或 ignored 目录，只把经过确认的参考图和生成资产放进公开仓库。

如果只有一张图，也可以先做，但会把结果标记为单视图近似，隐藏面不进入“准确还原”承诺。

## 每个物件的实施流程

```text
素材检查
  -> 独立 V0.x 工作树
  -> img2threejs assessment / spec
  -> 逐阶段生成和截图对照
  -> 独立四视图实验页
  -> 视觉评分达到 90
  -> 生产工厂瘦身
  -> 接入 SceneObjectResult 适配层
  -> TDD、资源预算、交互和多分辨率回归
  -> 尔玉本地验收
  -> 合并 main + 标签 + 推送
  -> 单独决定是否部署公网
```

每个物件都是独立阶段和独立提交。若某个物件无法达到门槛，保留现有程序化版本，不阻塞其他阶段。
